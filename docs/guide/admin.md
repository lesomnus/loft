# 관리자·소유자 안내서

관리자는 워크스페이스를 꾸리는 사람입니다. 사람을 들이고 역할을 주고, 유형과 예약할 수 있는 것과 도메인을 정합니다. 소유자는 그에 더해 워크스페이스 자체를 맡습니다. 이름과 지역, 기록을 얼마나 둘지, 결제 담당, 내보내기와 닫기가 소유자의 일입니다. 이 문서의 예는 체험용 워크스페이스의 관리자 **이건우**(`gunwoo-lee`)와 소유자 **관리자**(`admin`)입니다([체험용 워크스페이스](README.md#따라-하기-체험용-워크스페이스)).

## 역할

| 역할 | 하는 일 |
| --- | --- |
| 소유자 | 관리자의 일 모두와 워크스페이스의 이름·지역·기록 보관, 결제 담당 제안, 내보내기, 닫기와 복구 |
| 관리자 | 사람과 역할, 초대, 유형, 모델 삭제, 예약 자원, 도메인. 감사 기록과 접속기록 읽기와 점검 기록, 결제 설정 읽기 |
| 매니저 | 자산, 라벨, 지급·대여, 예약 승인, 재고, 실사, 작업, 구매, 리포트([매니저](manager.md)) |
| 구성원 | 예약, 인수 확인, 고장 신고, 소모품 사용, 읽기([구성원](member.md)) |
| 감사자 | 읽기, 리포트, 감사 기록과 접속기록 점검. 바꾸는 일은 하지 못함([감사자](auditor.md)) |

무엇을 누가 할 수 있는지는 [`server/policy/policy.go`](../../server/policy/policy.go)의 표 하나가 정하고, 표에 없는 것은 거부됩니다. 한 워크스페이스에 소유자가 여럿일 수 있습니다.

## 하루

### 워크스페이스 만들기

- 처음 로그인한 계정이 어느 워크스페이스에도 없으면 자기 워크스페이스가 하나 생깁니다(가입). 약관 동의를 묻는 배포라면 동의한 뒤에 생깁니다.
- 더 만들려면 워크스페이스 전환기의 **+ 새 워크스페이스**에서 이름을 적고 **만들기**를 누릅니다. 계정마다 3개까지 더 만들 수 있고, 그 이상은 결제가 필요합니다("더 만들려면 결제가 필요합니다"). 닫은 워크스페이스는 세지 않습니다.
- 주소(`/@…`)는 영문 소문자와 숫자 7자로 무작위로 정해집니다. 헷갈리는 i·l·o·0·1은 쓰지 않고 첫 글자는 영문입니다. 붐비면 저절로 8자가 됩니다.
- **주소는 바꿀 수 없습니다.** 바꿔야 하면 배포 운영자에게 요청합니다. 운영자가 바꾸면 이전 주소는 1년 동안 보류되고 새 주소로 넘겨 줍니다.

```sh
loft workspace new 연구실       # 만든 워크스페이스의 주소와 이름
loft workspace ls
```

### 이름

소유자는 **설정 › 워크스페이스**에서 이름을 바꾸거나 지웁니다(D58). 지우면 소유자의 이름으로 "○○의 워크스페이스"라고 부릅니다(D57).

- 이름은 누구의 정보도 아니어서 작업 기록과 감사 기록에 그대로 남고, 사람의 정보를 지워도 거기서는 지워지지 않습니다. 그래서 **사람의 이름은 넣지 않습니다.** 넣으면 화면이 그 워크스페이스 사람의 이름이 들어 있다고 알려 줍니다.
- 바꾸면 작업 기록(`workspace.configure`)이 남습니다. 관리자와 운영자는 바꾸지 않습니다.

```sh
loft workspace rename <주소> "연구지원팀 장비"
loft workspace rename --clear <주소>            # 이름을 지우고 소유자의 이름으로 부름
```

### 사람 들이기

**초대**(D30):

1. **사람 › + 초대**(또는 사람 상세의 **초대**)에서 이메일과 역할을 적고 **초대 보내기**를 누릅니다. 역할은 자기 역할까지 줄 수 있습니다.
2. 받은 사람은 메일의 링크를 열고 로그인(계정이 없으면 가입)한 뒤 **받은 초대**에서 수락하거나 거절합니다. roster가 그 주소를 확인된 것으로 갖고 있는 계정은 링크 없이도 초대함에서 봅니다.
3. **사람 › 초대** 탭에서 보낸 초대가 기다리는 중인지, 수락·거절했는지 봅니다. 기다리는 초대는 30일 뒤 만료되고, 여기서 취소할 수 있습니다.

초대 메일의 링크는 언제나 서비스 주소입니다. 초대받은 계정은 아직 그 워크스페이스의 구성원이 아니고, 초대함은 서비스 주소에 있기 때문입니다.

**로그인 발급**(내장 roster일 때): 사람 상세의 **로그인 발급**은 내장 roster에 계정을 만들고 이 워크스페이스의 구성원으로 넣습니다. 비밀번호를 한 번 보여 줍니다. **비밀번호 재설정**은 그 계정이 이 워크스페이스에만 있을 때 할 수 있습니다(다른 워크스페이스의 사람을 이 워크스페이스의 관리자가 막을 수는 없으니까요). roster를 따로 운영하는 배포에서는 둘 다 거부되고, roster에서 합니다.

조직도는 **+ 팀**과 **+ 거래처**로 만듭니다. 사람은 팀에 속하고, 거래처는 작업과 구매의 업체로 고릅니다.

```sh
loft api invitation add '{"email": "newhire@example.com", "role": "member"}'
loft api invitation ls -o wide '{"filters": [{"tenant": {"alias": "loft"}}]}'
loft api invitation revoke <초대 ID>

loft api party search -o wide '{"q": "개발팀", "kind": "team"}'
loft api party add '{"name": "한지민", "kind": "person", "email": "jimin-han@example.com", "parent_id": "<개발팀 ID>", "code": "E1051"}'
loft api party invite <사람 기록 ID> '{"alias": "jimin-han", "role": "member"}'   # 로그인 발급: 비밀번호를 한 번 출력
loft api party add '{"name": "연구팀", "kind": "team", "parent_id": "<본사 ID>"}'
loft api party add '{"name": "한빛렌탈", "kind": "vendor"}'
```

### 역할 바꾸기

사람 상세의 **역할 변경**입니다. 역할은 워크스페이스마다라서, 같은 계정이 다른 워크스페이스에서는 다른 역할일 수 있습니다.

```sh
loft api party set-role <사람 기록 ID> '{"role": "manager"}'   # owner, admin, manager, member, auditor
```

### 떠나는 사람

- **로그인 중지**와 **개인정보 삭제**는 이 워크스페이스의 구성원 자격만 끝냅니다. 계정은 그 사람의 것이라 남습니다.
- 개인정보 삭제는 사람 기록을 가명화하고(이름 `익명 …`, 연락처 삭제), 구성원 자격의 이름과 그 사람에게 보낸 초대의 주소, 감사 기록의 사본까지 지웁니다. 작업 기록과 자산 이력은 사람을 이름이 아니라 ID로 기억하고 읽을 때 지금의 이름을 붙이므로, 그 사람은 이력에서도 가명으로 보입니다. 다만 2026-10-12 이전에 쓴 작업 기록은 쓴 그대로라 문장에 이름이 남아 있습니다.
- 계정을 roster에서 지운 사람은 속한 모든 워크스페이스에서 **떠나는 중**이 되고, 유예(기본 30일)가 지나면 워크스페이스마다 개인정보 삭제와 같은 일이 일어납니다. 그 계정이 마지막 소유자였던 워크스페이스는 남은 사람 중 역할이 가장 높은 사람(관리자 > 매니저 > 구성원, 감사자는 제외), 같은 역할이면 먼저 들어온 사람이 소유자가 됩니다.
- 작업 기록의 사유에 그 사람의 이야기가 적혀 있어 지워 달라는 요청이 오면, 워크스페이스의 지시로 배포 운영자가 지웁니다([사유 삭제](operator.md#작업-기록의-사유를-지울-때)). 워크스페이스 안에서 이 일을 할 수 있는 역할은 아직 없습니다.

```sh
loft api party deactivate <사람 기록 ID>      # 로그인 중지
loft api party pseudonymize <사람 기록 ID>    # 개인정보 삭제 (되돌릴 수 없음)
```

### 유형, 모델, 예약 자원

**설정**에서 합니다.

- **유형**: 자산의 종류(노트북, 회의실, 키트)와 그 속성(CPU, 수용 인원, 보증 만료일 같은 것)을 정합니다. 관리자의 일입니다.
- **모델**: 제조사와 모델(Dell U2723QE)입니다. 매니저도 만들고 바꾸며, 지우는 것은 관리자입니다.
- **예약 자원**: 무엇을 예약할 수 있게 할지와 그 정책입니다. 자산 화면의 **예약 가능하게**도 같습니다. 승인 필요 여부, 운영 시간, 앞뒤 정리 시간, 최소·최대 이용 시간, 얼마나 앞까지 받을지, 수량(풀), 함께 쓸 수 없는 묶음을 정합니다. 체험용 워크스페이스에서는 대회의실만 승인이 필요합니다.

```sh
loft api asset-type ls -o wide
loft api asset-type add '{"name": "의자", "kind": "item"}'
loft api asset search -o wide '{"q": "PJ-002"}'
loft api bookable add '{"asset": {"id": "<PJ-002의 ID>"}, "approval": true, "max_minutes": 10080}'   # 일주일까지, 승인 받고
loft api bookable ls -o wide '{"filters": [{"asset": {"id": "<PJ-002의 ID>"}}]}'
loft api bookable update <예약 자원 ID> '{"max_minutes": 4320, "enabled": true}'
```

### 도메인과 라벨

워크스페이스는 **설정 › 도메인과 라벨**에서 자기 도메인을 둘 수 있습니다(loft#155). 도메인이 없어도 라벨은 언제나 켜져 있고, 그때는 서비스 주소로 인쇄됩니다.

- **종류**: 무엇에 쓰이는지는 고르는 것이 아니라 종류가 정합니다.
  - **자체 도메인**(`assets.example.com`)은 앱 도메인입니다. 쓰기로 하면 그 워크스페이스의 앱 전체가 그 도메인에 있고, 라벨도 그 도메인으로 인쇄됩니다.
  - **기본 주소**는 배포가 정한 이름 아래의 하위 도메인(`<이름>.<배포의 라벨 주소>`)입니다. DNS 작업이 필요 없고 라벨만 씁니다. 새 워크스페이스에 저절로 생기지 않고, 원하는 워크스페이스가 추가합니다. 배포가 기본 라벨 주소를 두지 않았으면 쓸 수 없습니다.
- **할 일**: 도메인을 더하고, 설정 화면에 나오는 레코드 둘을 DNS에 만듭니다. 몇 분마다 저절로 확인하고, 확인되면 쓸 수 있습니다.
  - CNAME `<도메인>` → 화면에 나오는 이름. CNAME을 둘 수 없는 apex라면 DNS 업체의 ALIAS나 CNAME 펼치기로 같은 주소를 가리키게 합니다.
  - TXT `_loft-challenge.<도메인>` = 화면에 나오는 토큰
- **확인된 뒤에도 두 레코드를 지우지 않습니다.** 쓰는 동안 한 시간마다 다시 확인하고, 여섯 번 연속(다섯 시간 넘게) 맞지 않으면 사용을 멈춥니다(DNS 확인 실패). 그러면 로그인과 링크는 서비스 주소로 돌아가고, 소유자와 관리자에게 알림과 메일이 갑니다. 레코드를 되돌리면 일주일 동안 저절로 다시 확인하고, 설정에서 바로 확인할 수도 있습니다. 답이 없는 DNS(시간 초과, DNS 업체 장애)는 세지 않습니다.
- **그 도메인에서 일하는 사람**:
  - 로그인은 서비스 주소가 합니다. 로그인하지 않은 채 도메인을 열면 서비스 주소로 넘어가 로그인(이미 했으면 그대로)한 뒤, 1분 동안 한 번만 쓰이는 코드로 그 도메인 전용 세션을 받아 돌아옵니다.
  - 그 워크스페이스는 그 도메인에서 엽니다. 서비스 주소에서 그 워크스페이스의 화면(`/@주소/...`)을 열면 그 도메인의 같은 화면으로 넘어가고, 워크스페이스 전환에서 고르면 바로 그 도메인으로 갑니다. 호출, 로그인, 계정, 터미널, 라벨(`/l/...`)은 서비스 주소에서도 그대로 답합니다. 활성이 아닌 도메인(이전 주소, DNS 확인에 실패한 도메인)으로는 보내지 않습니다.
  - 그 세션은 그 워크스페이스만 다룹니다. 워크스페이스 전환에는 그 워크스페이스 하나와, 계정의 다른 워크스페이스를 고르는 서비스 주소의 목록("다른 워크스페이스로")으로 가는 링크가 나옵니다. 워크스페이스 만들기, 받은 초대, 약관 동의, 터미널 로그인은 서비스 주소에서 합니다.
  - 도메인에서 로그아웃하면 서비스 주소의 로그인도 함께 끝납니다. 서비스 주소에서 로그아웃해도 도메인의 세션이 끝납니다.
  - 알림 메일의 링크, 새로 인쇄하는 라벨, 첨부의 내려받기 주소가 그 도메인으로 만들어집니다.
- **도메인을 바꾸면** 이전 도메인은 "이전 주소"로 남아 그 주소로 인쇄한 라벨이 계속 열립니다. 이전 앱 도메인은 90일(`app.workspaces.domain_redirect`) 동안 페이지를 새 도메인으로 보냅니다. 서비스 주소로 인쇄한 라벨도 그대로 열립니다.
- 배포가 워크스페이스 도메인의 인증서를 받게 켜 두어야 합니다. 그것은 운영자의 일입니다([운영자](operator.md#워크스페이스-도메인)).

```sh
loft api tenant-domain status                               # 지금 라벨이 인쇄되는 주소
loft api tenant-domain add '{"host": "assets.example.com"}'  # 자체 도메인
loft api tenant-domain add '{"sub": "woori"}'                # 기본 주소 (배포가 두었을 때)
loft api tenant-domain ls -o wide
loft api tenant-domain get <도메인 ID>                         # token이 TXT 레코드의 값
loft api tenant-domain verify <도메인 ID>                      # 지금 확인
loft api tenant-domain activate <도메인 ID>
loft api tenant-domain retire <도메인 ID>
```

### 지역과 예약 (소유자)

**설정 › 워크스페이스 › 지역과 예약**에서 세 가지를 정합니다(loft#144). 비워 두면 배포의 기본값(`app.locale`, `app.no_show_after`)을 따릅니다.

- **시간대**: 그 워크스페이스의 날짜가 이 시간대를 따릅니다. 화면에 보이는 날짜와 화면에서 입력하는 시각(브라우저가 어느 시간대에 있든), 자산 대장 CSV의 날짜, 알림 문장의 시각, 하루 단위 집계의 날짜 경계, 대량 등록이 읽는 날짜, 새 예약 공간의 기본 시간대가 모두 그렇습니다. 배포가 정하지 않았으면(`app.locale.timezone`) Asia/Seoul입니다.
- **통화**: 새 구매와 새 작업의 금액이 이 통화로 기록됩니다. 이미 기록된 금액은 기록할 때의 통화 그대로이고, 환산하지 않습니다. 비용이 있는 작업의 통화를 바꾸려면 그 통화로 비용도 함께 적어야 합니다. 금액은 그 통화의 최소 단위의 정수입니다(KRW는 원, USD는 센트). 배포가 정하지 않았으면(`app.locale.currency`) KRW입니다.
- **노쇼 해제**: 회의실 예약이 시작되고 몇 분 안에 체크인하지 않으면 예약을 풉니다(1~1440분). **체크인을 받지 않음**으로 두면 풀지 않고, 회의실 예약은 끝나면 이용한 것으로 완료합니다. 수령하지 않은 장비 예약은 기간이 끝나면 만료됩니다(노쇼로 세지 않습니다, design 7.15).

바꾸면 작업 기록(`workspace.configure`)이 남습니다.

```sh
loft api tenant configure @loft '{"timezone": "America/New_York", "currency": "USD"}'
loft api tenant configure @loft '{"no_show_minutes": 10}'
loft api tenant configure @loft '{"no_show_minutes": -1}'   # 체크인을 받지 않음
loft api party me                                           # 지금 따르는 시간대와 통화
```

### 기록 보관 (소유자)

워크스페이스가 이력을 얼마나 보관할지는 **워크스페이스가 정합니다**(design 8, D36). **설정 › 워크스페이스 › 기록 보관**에서 정하고, 접속기록을 얼마나 보관할지와 닫은 뒤 얼마나 복구할 수 있는지도 같은 자리에서 정합니다(loft#144). 보관하는 기록은 모두 보입니다. 조회 기간을 따로 두지 않습니다.

- **이력**: 비우면 영원히 보관합니다.
- **접속기록**: 비우면 배포의 기간을 따릅니다. 배포의 바닥값보다 짧게는 정할 수 없습니다(예: "접속기록은 법이 정한 365일보다 짧게 둘 수 없습니다").
- **닫은 뒤 복구 기간**: 비우면 배포의 기간(`app.workspaces.restore_within`, 기본 30일)을 따릅니다.
- **줄인 기간은 유예가 지난 뒤에 적용됩니다**(`app.retention.grace`, 기본 30일). 그때까지는 그 전 기간을 지키므로, 그 안에 되돌리면 아무것도 지워지지 않습니다. 저장하기 전에 화면이 언제부터 무엇이 몇 건 지워지는지 보여 줍니다.
- 배포가 아직 보관 기간으로 기록을 지우지 않으면 화면이 그렇다고 말합니다("이 배포는 아직 보관 기간으로 기록을 지우지 않습니다"). 지우는 일은 배포가 켜야 돌아갑니다.
- 워크스페이스가 파기될 때 감사 기록을 어떻게 할지는 운영자와의 계약이 정합니다. 계약과 법적 보존(hold)은 읽기만 합니다.

```sh
loft api tenant preview @loft '{"keep_days": 1095, "access_keep_days": 365}'     # 저장하기 전에: 언제부터 무엇이 지워지나
loft api tenant configure @loft '{"keep_days": 1095, "access_keep_days": 365, "restore_days": 60}'
loft api tenant-contract ls -o wide
loft api legal-hold ls -o wide
```

### 기록 읽기

**설정 › 작업 기록**은 무엇을 왜 했는지(자산 이력의 원천), **감사 기록**은 누가 무엇을 바꿨는지, **접속기록**은 누가 누구의 개인정보를 읽고 쓰고 내려받았는지입니다. 감사 기록과 접속기록은 관리자 이상과 감사자만 봅니다. 접속기록을 한 달씩 점검하는 법은 [감사자 안내서](auditor.md#접속기록-점검)에 있고, 관리자도 같은 일을 합니다.

### 내보내기, 닫기, 복구 (소유자)

**내보내기**: 설정 › 워크스페이스의 **워크스페이스 데이터 내려받기**는 모든 데이터를 zip으로 줍니다. 모든 사람의 데이터가 들어 있으므로 내려받는 이유를 묻고, 그 이유는 접속기록에 남습니다.

**닫기**(D29): 소유자는 설정 › 워크스페이스의 **워크스페이스 닫기**에서 확인을 위해 워크스페이스 이름을 그대로 입력하고 닫습니다. 닫는 이유는 적어도 되고 안 적어도 됩니다.

- 닫으면 소유자 말고는 아무도 들어오지 못합니다. 소유자는 복구 기간 안에 **복구**하거나 **데이터 내려받기 (zip)** 를 합니다. 닫기 화면이 복구 기간을 알려 줍니다.
- 그 뒤에는 모든 데이터와 파일이 지워지고(법적 보존이 걸려 있으면 풀릴 때까지 기다림), 주소는 1년 동안 보류됩니다. 감사 기록은 계약이 정한 대로 떠납니다. 기본은 은퇴(retire)라서, 법이 정한 최소 보관 기간이 걸린 기록(접속기록 등)은 그 기간이 지날 때까지 남고 나머지는 함께 지워집니다.
- 계정 탈퇴로 구성원이 아무도 남지 않은 워크스페이스는 저절로 닫힙니다. 배포 운영자도 대신 닫고 엽니다.
- 닫힌 동안은 배포의 일(홀드와 요청의 만료, 노쇼 해제, 연체, 반납 예정과 작업의 알림, 도메인 확인)도 그 워크스페이스를 건너뛰어 아무것도 바뀌지 않고, 알림과 메일도 가지 않습니다.
- 복구하면 그동안 시간이 지나 아무도 받을 수 없었던 것(시간이 지난 홀드, 시작 시각이 지난 승인 대기, 체크인 유예가 지난 회의실, 기간이 끝난 장비)은 복구가 만료로 정리하고 알리지 않습니다. 노쇼로 세지 않습니다. 그 밖의 것은 다음 정리 때 한 번에 처리하고 그때도 참인 것(연체, 반납 예정, 작업 등)을 한 번 알립니다(design 7.14, 7.15).
- 보존 기간이 지난 기록은 닫혀 있어도 지웁니다.

```sh
loft workspace export --reason "닫기 전에 보관" --out 연구실.zip <주소>
loft api tenant close @<주소> '{"confirm": "<워크스페이스 이름>", "reason": "실험 끝"}'
loft api tenant restore @<주소>
```

### 결제 (관리자 이상)

배포가 과금을 켜 두었으면 **설정 › 결제**가 보입니다. 누가 무엇을 내는지는 청구 서비스 levyan의 것이고, Loft는 levyan에 묻고 보여 줄 뿐입니다.

- **결제 담당**: 지금 내는 사람과 다음 기간부터 낼 사람
- **이번 기간 사용량과 예상 금액**: 미터마다(활성 자산, 첨부 저장량, 구성원, 이력 보존 기간) 사용량과 무료(가격의 무료량 + 프로모션)·사용량 크레딧·유료. 예상 합계는 크레딧을 빼기 전입니다.
- **지난 명세서**: 명세서마다 "보기"로 그 기간의 줄을 봅니다.
- levyan의 운영자가 준 추가 무료량과 사용량 크레딧(남은 양, 이번 기간 뒤에 남을 양), 워크스페이스에 남은 크레딧
- **결제 담당 제안**(소유자): 구성원에게 결제 담당을 제안하면, 제안받은 사람이 자기 결제 화면에서 받아들입니다. 이번 기간이 끝난 뒤부터 냅니다. 로그인하는 구성원에게만 제안할 수 있습니다.
- **내가 결제 담당 맡기**(소유자): 결제 계정을 골라 한 번에 맡습니다. 이것도 이번 기간이 끝난 뒤부터입니다.

결제가 막히면 화면 위에 띠(배너)가 나옵니다.

- 결제 담당이 없거나 청구서의 결제가 실패했으면 소유자와 관리자에게 언제부터 제한되고 언제부터 읽기 전용이 되는지와 할 일을 말합니다. 그 워크스페이스를 내는 결제 계정으로 지금 결제할 수 없으면(결제수단 없음 같은 것) 무엇이 실패하기 전에 그것도 말합니다. 그것만으로 제한되지는 않습니다.
- **제한**(1단계)되면 모든 구성원에게 그것과 그 까닭을 말합니다. 제한된 워크스페이스는 청구되는 것을 늘리지 못합니다. 자산 등록(대량 등록, 재고 전환, 자산으로 받는 구매 입고 포함), 분실·폐기한 자산을 다시 쓰는 상태로 바꾸기, 첨부 올리기, 로그인 발급·초대 보내기·받아들이기, 이력을 지금보다 오래 보관하기입니다. 보기, 내보내기, 지급·반납, 예약, 이동, 처분·삭제, 닫기, 결제는 그대로입니다.
- **읽기 전용**(2단계)은 결제가 처음 실패한 청구서가 60일 뒤에도 결제되지 않았거나, 결제 담당이 없어진 지 60일이 지난 워크스페이스입니다. 보기(리포트, 접속기록 읽기 포함), 내보내기와 다운로드, 결제, 닫기, 떠나기(구성원 자격 끝내기, 개인정보 삭제), 비밀번호 바꾸기, 자기 알림을 읽음으로 표시하기와 메일 끄기만 됩니다. 그 밖의 쓰기는 모두 막힙니다. 소유자·관리자·지불자에게 밀린 청구서를 결제하면 풀린다는 것과 갈 곳을 말합니다.
- 읽기 전용인 동안에도 배포의 일은 돌아 예약이 만료되고 대여가 연체됩니다. 다만 할 수 없는 일을 하라는 알림(반납 예정, 연체, 예약된 자산이 나가 있음, 풀 수량 부족, 다가오는 작업)은 보내지 않고, 다시 쓸 수 있게 되면 그때도 참인 것을 한 번 알립니다.

```sh
loft api payment get-payer                     # 누가 내는가
loft api payment get-usage                     # 이번 기간 사용량과 예상 금액
loft api payment list-statements               # 지난 명세서
h=$(loft api holder get -o 'template={{.id}}' @loft/haeun-lee)
loft api payment offer "{\"holder\": \"$h\"}"  # 소유자: 이하은에게 결제 담당 제안
```

`offer` 의 `holder` 는 구성원 자격의 ID를 base64로 받습니다(위처럼 `template` 으로 꺼냅니다). 결제 계정과 청구서는 [결제 담당 안내서](payer.md)에 있습니다.
