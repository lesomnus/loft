# 감사 기록 위변조 감지 대응 (운영자)

`audit.archive`를 둔 배포에서 감사 기록 보관소가 DB의 기록(manifest)이나 체크포인트와 맞지 않을 때 할 일입니다. 어떻게 확인하고 무엇을 켜 두는지는 README의 [감사 기록 보관소 확인](../../README.md#감사-기록-보관소-확인-운영자)에 있습니다.

**기본값은 멈추고 기다리는 것입니다.** 행이 최신 체크포인트와 맞지 않으면 운영자가 `loft trail accept`를 실행할 때까지 새 체크포인트를 남기지 않습니다. 저절로 풀리지 않고, 끄는 설정도 없습니다. 조작된 상태 위에 체크포인트가 쌓이면 두 작업 뒤에는 무엇이 바뀌었는지 더 이상 드러나지 않기 때문입니다. 앱은 그동안에도 계속 동작합니다.

## 무엇이 보이나

감지되면 `` `trail verify` ``(백틱까지)라는 문자열을 담은 경고가 반드시 나옵니다. 로그 경보는 이 문자열 하나에 걸면 됩니다.

| 로그 | 뜻 |
| --- | --- |
| `trail: the archive is not what its manifest says` | 보존 패스가 시작할 때 가볍게 맞춰 본 결과입니다. `finding=`마다 한 줄씩(최대 20줄), 끝에 `findings=` 개수와 종류별 수가 나옵니다 |
| `the manifest no longer adds up to the latest checkpoint, and no checkpoint is taken over it until an operator accepts it` | 행이 최신 체크포인트와 맞지 않습니다(`rewritten`). 작업의 오류에 `the checkpoint after it: …` 뒤로 나옵니다 |
| `the checkpoint store has checkpoints the database never numbered: a database restored from before them` | DB가 모르는 번호의 체크포인트가 있습니다(`behind`). DB를 백업에서 복원했을 때 나옵니다 |
| `trail: settling the manifest, not while it does not add up to its latest checkpoint` | 맞지 않는 동안 패스가 진행 중이던 추가·삭제를 정리하지 않습니다 |
| `trail: the manifest is empty and the archive has checkpoints, so it is not filled from what the archive holds` | DB의 기록이 비어 있는데 체크포인트가 있습니다(`emptied`) |
| `trail: chunks the manifest does not account for, left out of what is read` / `left alone` | DB가 모르는 청크를 읽기(내보내기)와 파기에서 뺐습니다 |
| `a row whose signature is a finding is not moved along` | 서명이 맞지 않는 행은 옮기거나 파기하지 않습니다 |
| `its bytes are not its digest any more` | 읽던 청크의 내용이 바뀌었습니다(`altered`). 내보내기가 이 오류로 실패합니다 |

일정에 걸어 둔 `loft trail verify`는 무언가 찾으면 `N findings: …`를 출력하고 0이 아닌 코드로 끝납니다. 출력에는 찾은 것 전체의 다이제스트(`digest sha256:…`)와 최근의 받아들임(`accepted at checkpoint N, 시각, by 누구: 이유 (종류 건수)`)도 나옵니다. `accept`는 이 다이제스트를 받습니다(payday#115).

## 감지된 동안 무엇이 되고 무엇이 안 되나

| | |
| --- | --- |
| 앱 | 로그인, 화면, API 모두 그대로 동작합니다. 감사 기록도 DB에 계속 쌓입니다 |
| 보존 패스 (`audit.every`, 기본 하루) | 행을 보관소로 옮기고 기간이 지난 청크를 파기하는 일은 계속하지만, 끝에 체크포인트를 남기지 못해 경고합니다. 그 사이의 변경은 체크포인트로 보호되지 않습니다 |
| 개인정보 삭제, 계정 탈퇴(`app.accounts.forget_after`) | 보관소에 그 사람의 기록이 있으면 **오류로 실패**하고, DB 쪽은 트랜잭션째 되돌려집니다. 보관소에 이미 쓴 것은 되돌려지지 않습니다 |
| 닫힌 워크스페이스의 파기 (`app.workspaces.restore_within` 이후) | 보관소를 정리하는 단계에서 오류로 끝나고, 다음 주기에 다시 시도합니다 |
| 내보내기 | DB가 기록해 둔 청크만, 내용이 그대로인 것만 읽습니다. 내용이 바뀐 청크가 있으면 실패합니다 |

오래 멈춰 둘수록 체크포인트 없이 쌓이는 변경이 늘어나고, 처리 기한이 있는 삭제 요구가 막힌 채로 남습니다. 미루지 않습니다.

## 원칙

1. **`accept`부터 하지 않습니다.** `accept`는 "보관소가 맞다"는 배포의 서명이고, 그 뒤로는 그 상태가 기준이 됩니다. 원인을 모르면 실행하지 않습니다.
2. **증거부터 남깁니다.** `accept`도 복구도 그 뒤입니다.
3. **혼자 정하지 않습니다.** `accept`는 두 번째 사람이 원인과 `--why`를 읽은 뒤에 실행합니다. 두 사람은 같은 `verify` 출력과 같은 다이제스트를 봅니다. `accept --of`는 그 다이제스트로 다시 검사하므로, 살펴본 뒤에 바뀐 것은 받아들여지지 않습니다.
4. 서버를 끌 필요는 없습니다. DB와 보관소를 모두 쓸 수 있는 누군가를 막는 것은 서버를 끄는 것이 아니라 그 자격 증명을 바꾸는 것입니다. 침해 대응으로 끌지는 보안 책임자가 정합니다.

## 1. 확인하고 남기기

`loft trail`은 서버와 같은 설정(`loft.yaml`, `LOFT_*`)으로, DB와 보관소에 닿는 곳에서 실행합니다. 서버를 멈추지 않아도 되고, `verify`는 아무것도 바꾸지 않습니다.

```sh
at=$(date -u +%Y%m%dT%H%M%SZ)
loft trail verify --full 2>&1 | tee "trail-verify-$at.txt"   # 모든 청크를 읽으므로 오래 걸릴 수 있음
```

`accept`나 복구 전에 다음을 한곳에 모읍니다. 조사하는 사람만 읽을 수 있는 곳에 둡니다.

- 위의 `verify` 출력과 실행 시각(UTC)
- 서버 로그: 최소한 마지막으로 깨끗했던 체크포인트(`trail: a checkpoint`) 이후 전부
- DB 덤프: PostgreSQL은 `pg_dump`, SQLite는 서버를 멈추지 않고 `sqlite3 <DB 파일> ".backup <사본>"`
- 보관소 사본(`audit.archive`). S3라면 객체 버전 목록까지
- 체크포인트 저장소의 목록과 각 파일의 해시. 삭제를 거부하는 저장소라면 그대로 둡니다
- 접근 기록: DB 접속 로그, 보관소·체크포인트 저장소의 접근 기록(S3 CloudTrail, 파일 시스템 감사 로그), 서버 접속 기록, 그 기간의 배포·운영 작업 기록

## 2. 무엇을 찾았나

`verify`의 한 줄은 `종류 네임스페이스 다이제스트 [checkpoint N]: 설명`입니다. 네임스페이스는 워크스페이스 id입니다. `_shared`는 여러 워크스페이스에 걸친 행, `_deployment`는 어느 워크스페이스의 것도 아닌 행, `_receipts`는 무엇을 파기했는지의 기록, `_legacy`는 보관소가 지금 형식이 되기 전의 파일입니다. 체크포인트에 대한 것은 네임스페이스 없이 `checkpoint N`으로 나옵니다.

| 종류 | 뜻 | 흔한 정상 원인 | 의심할 때 |
| --- | --- | --- | --- |
| `missing` | DB에는 있다고 적힌 청크가 보관소에 없음 | 저장소 장애, 복원에서 빠진 청크 | 누군가 지웠음 — 기록 은폐 |
| `unaccounted` | 보관소에 있는데 DB가 모르는 청크 | 백업에서 청크를 되돌려 놓음, DB를 그 청크 이전으로 복원 | 누군가 넣었음 — 기록 위조 |
| `relabelled` | 청크·체크포인트의 라벨이 기록과 다름 | 보관소를 옮기는 도구가 메타데이터를 바꿈 | 파기 시점을 앞당기거나 미루려는 시도 |
| `altered` | 청크 내용이 다이제스트와 다름 (`--full`만) | 디스크 손상 (드묾) | 내용 변조. 가장 심각합니다 |
| `forged` | 서명이 틀리거나, 아무도 믿지 않는 키의 서명. 또는 증인이 들었다고 답한 문장의 서명이 틀림([증인](#forged--증인의-답의-서명이-틀림)) | 서명 키를 바꾸고 이전 공개 키를 `audit.checkpoints.trust`에 넣지 않음 | 서명 위조, 증인의 저장소에 누가 씀 |
| `unsigned` | 서명 없는 행, 아무도 서명하지 않은 체크포인트 | 키를 처음 둔 배포, 키 없이 쓰던 보관소의 이전 행과 체크포인트 (README의 한 번 `accept`) | 서명을 지움 |
| `rewritten` | 행이 최신 체크포인트와 맞지 않음, 같은 번호의 체크포인트가 둘. 또는 증인이 같은 번호를 두 문장으로 들음, 저장소가 증인이 들은 것과 다른 것을 가짐([증인](#rewritten--증인이-같은-번호를-두-번-들음)) | 거의 없음. DB를 손으로 고친 경우, 증인이 없던 동안의 복원 | DB와 보관소를 함께 고침, 번호를 되감음 |
| `reordered` | 체크포인트가 자기보다 뒤의 것을 앞의 것으로 가리킴 | 거의 없음 | 체크포인트 저장소 조작 |
| `unkept` | DB가 번호를 매긴(10분 이상 지난) 체크포인트가 저장소에 없음, 또는 체크포인트가 앞 체크포인트를 가리키며 건너뛴 번호. 또는 증인이 들은 체크포인트가 저장소에 없음, 저장소의 최신보다 뒤의 것이면 `the chain was cut short there`([증인](#unkept--the-chain-was-cut-short-there)) | 체크포인트 저장소 장애, 오래된 사본에서 되살린 체크포인트 저장소, 번호를 매긴 뒤 쓰기 전에 멈춘 패스 | 체크포인트 삭제, 사슬을 맨 위에서 자름 |
| `unheard` | 저장소의 최신 체크포인트가 `audit.checkpoints.hear_within`보다 오래되었는데 답하는 증인 누구도 듣지 못함([증인](#unheard)) | 증인의 볼륨이 빠졌거나, 디스크가 찼거나, 권한이 없음 | 자른 것이 드러나지 않게 증인을 막음 |
| `behind` | 저장소에 DB가 모르는 번호의 체크포인트 | DB를 백업에서 복원 | DB를 과거로 되돌림 |
| `lost` | DB가 뒤처졌을 때(`behind`), 배포가 보증하는 최신 체크포인트가 보관소에 있다고 한 청크가 이제 없고 DB에도 그 행이 없음 | 백업 뒤에 쓰인 청크를 패스가 기간이 지나 파기함(로그에 남음) | 누군가 청크를 지우고 DB를 되돌려 숨김 |
| `emptied` | DB의 기록이 비었는데 체크포인트가 있음 | 체크포인트 이전 백업으로 복원, 새 DB에 옛 보관소를 연결 | 기록을 통째로 지움 |

정상 원인이 문서·작업 기록·티켓으로 확인되면 3으로, 아니면 4로 갑니다. 찾은 종류가 그 원인으로 다 설명되지 않으면 4입니다.

## 3. 정상 원인이 확인되었을 때

먼저 `accept`가 아닌 해결이 있는지 봅니다.

- **키를 바꾼 뒤의 `forged`**: 이전 공개 키를 `audit.checkpoints.trust`에 넣고 다시 `verify`합니다. `accept`하지 않습니다.
- **`altered`**: `accept`로 고쳐지지 않습니다. 청크는 다이제스트로 찾으므로, 백업에서 같은 다이제스트의 원본을 같은 자리에 되돌려 놓습니다. 백업이 없으면 바뀐 청크를 증거로 따로 보관하고 보관소에서 뺀 뒤(그러면 `missing`), 그 기간의 기록을 잃었다는 것을 `--why`에 적어 `accept`합니다.
- **`behind`, `emptied` (DB 복원)**: 아래 [DB를 백업에서 복원했을 때](#db를-백업에서-복원했을-때)를 따릅니다.

그 밖에는, 1에서 남긴 `verify` 출력의 다이제스트로:

```sh
loft trail accept --of sha256:… --full --by "운영자 A" --why "2026-10-13 저장소 장애 복구 중 백업에서 청크 3개를 되돌림. 증거: OPS-123. 확인: 운영자 A, B"
loft trail verify --full
```

- `--of`는 살펴본 `verify`가 출력한 다이제스트이고, `--full`은 그 `verify`가 `--full`이었을 때 붙입니다. `accept`는 같은 방식으로 다시 검사해서, 찾은 것이 하나라도 다르면 받아들이지 않고 끝납니다(`an acceptance is of the findings that were looked at …`). 그 사이 무언가 바뀌었다는 뜻이므로 1부터 다시 합니다.
- `--by`는 누가 받아들였는지입니다. 주지 않으면 셸의 사용자와 호스트(`사용자@호스트`)입니다.
- `--why`에는 무엇을 찾았는지, 원인, 증거를 둔 곳, 누가 확인했는지를 적습니다. 누가·왜·어느 다이제스트를·무엇을 몇 건 받아들였는지가 로그에 남고, `accept`가 끝에 남기는 체크포인트에 서명과 함께 영구히 기록되며, 보관소의 영수증(`accept`)에도 남습니다. 그다음 `verify`가 그 받아들임을 보여 줍니다.
- 키(`audit.checkpoints.key`)를 둔 배포는 그 키가 있어야 `accept`할 수 있습니다. 받아들이는 것이 곧 서명하는 것입니다.
- `accept`는 서명이 문제였던 행에 지금 서명하고, DB가 모르는 청크를 기록에 넣고, 없는 청크를 지워진 것으로 적고, 라벨을 지금 것으로 적은 뒤, 이유를 담은 체크포인트로 끝납니다. 체크포인트 자체는 하나도 바꾸지 않습니다.

## 4. 침해가 의심되거나 원인을 모를 때

멈춘 상태를 유지합니다. 멈춘 동안에는 조작된 상태 위에 체크포인트가 쌓이지 않으므로, 계속 드러난 채로 남습니다.

1. **알립니다.** 보안 책임자, 개인정보 보호책임자, 법무.
2. **막습니다.** DB와 보관소, 체크포인트 저장소를 쓸 수 있는 자격 증명(DB 계정, S3 키, 서버 접속)을 바꿉니다. 서버에서 서명 키 파일을 읽을 수 있었다면 키도 새로 만듭니다. 이전 키를 `audit.checkpoints.trust`에 다시 넣을지는 노출된 시점과 함께 정합니다. 이전 키를 믿으면 그 키로 만든 위조도 믿게 됩니다.
3. **조사합니다.** 마지막으로 깨끗했던 체크포인트 시각 이후의 접근 기록, 찾은 청크의 네임스페이스(영향받은 워크스페이스), 무엇이 지워지거나 들어왔는지를 봅니다.
4. **통지를 판단합니다.** DB와 보관소를 모두 쓸 수 있었던 사람은 읽을 수도 있었다고 보고 유출 여부를 판단합니다. 유출이면 정보주체 통지와 개인정보보호위원회·한국인터넷진흥원 신고(개인정보 보호법 제34조, 알게 된 때부터 72시간 안), EU 정보주체가 있으면 GDPR 제33조(72시간 안 감독기관 신고), 고객 계약의 통지 조항을 따릅니다. 기한과 대상은 법무가 확인합니다. 접속기록을 위·변조로부터 보호하는 것 자체가 안전성 확보조치 의무이므로, 조작이 확인되면 그것도 기록합니다.
5. **되돌립니다.** 바뀐 부분을 백업에서 되돌려 놓습니다. 체크포인트에는 그 시점의 모든 청크의 다이제스트가 있으므로, 백업이 맞는지 체크포인트와 맞춰 볼 수 있습니다. 그 뒤 `verify --full`로 남은 것을 보고, 사고와 조치를 `--why`에 적어 `accept`합니다.

## 5. 다시 돌아간 뒤

- `loft trail verify --full`이 `the archive is what the database says it is`로 끝납니다.
- `accept`를 실행한 쪽의 로그에 `trail: a checkpoint`(`after=accept`)가, 그 뒤 서버 로그에 다음 작업이나 패스의 `trail: a checkpoint`가 나옵니다.
- 멈춘 동안 실패한 개인정보 삭제를 다시 실행합니다. 계정 탈퇴와 워크스페이스 파기는 각자의 주기에 다시 시도하므로, 로그에서 끝난 것을 확인합니다.
- 사후 검토를 남깁니다: 타임라인, 원인, `--why`에 적은 것, 막을 방법.

## DB를 백업에서 복원했을 때

최신 체크포인트보다 오래된 백업에서 DB를 복원하면, DB가 매긴 체크포인트 번호가 저장소보다 뒤처집니다. 작업마다 체크포인트를 남기므로 거의 모든 백업이 그렇습니다. 그동안은 체크포인트를 남기지 않고, 보관소를 건드리는 작업은 위의 표처럼 오류로 끝납니다.

```sh
loft trail verify --full 2>&1 | tee "trail-verify-$(date -u +%Y%m%dT%H%M%SZ).txt"   # behind, unaccounted, lost, 그리고 다이제스트
loft trail accept --of sha256:… --full --restored 38 --why "2026-10-13 DB를 10-01 백업에서 복원함. lost 2건은 10-02 패스의 파기로 확인. 복원 작업: OPS-124. 확인: 운영자 A, B"
loft trail verify --full                                     # 깨끗함
```

- 복원 직후의 `verify`에는 `behind`와 함께 이런 것이 나올 수 있습니다: 백업 뒤에 보관소에 쓰인 청크의 `unaccounted`, 백업 뒤에 보존 패스가 접거나 파기한 청크의 `missing`, 배포가 보증하는 최신 체크포인트가 있다고 한 청크가 이제 없는 `lost`. 백업 시점에 DB의 기록이 비어 있었다면 `emptied`도 나옵니다. 체크포인트 저장소를 DB보다 오래된 사본에서 되살렸다면 건너뛴 번호의 `unkept`도 나옵니다. **그 밖의 종류**(`altered`, `forged`, `rewritten` 등)는 복원으로 설명되지 않으므로 [4](#4-침해가-의심되거나-원인을-모를-때)로 갑니다.
- **`lost`와 `missing`은 하나씩 확인합니다.** 복원은 백업 뒤에 쓰인 것을 설명할 뿐, 백업 뒤에 없어진 것은 설명하지 않습니다. 없어진 청크는 보존 패스가 기간이 지나 파기한 것(서버 로그에 남음)이거나 누군가 지운 것입니다. 로그로 설명되지 않는 것이 있으면 [4](#4-침해가-의심되거나-원인을-모를-때)로 갑니다. DB를 되돌려 지운 흔적을 숨기면 `lost`로 보입니다.
- `--restored`에는 백업이 가진 체크포인트 번호를 적습니다. `behind` 줄의 `the database has numbered N checkpoints`의 N이고, 첫 체크포인트 전의 백업이면 0입니다. 복원으로만 받아들입니다: `--restored`가 없거나, 번호가 다르거나, DB가 뒤처지지 않았는데 `--restored`를 주면 거부합니다(`a database restored from a backup is accepted as the restore it is …`).
- `accept`는 저장소에 있는 가장 최근 체크포인트의 다음 번호로 체크포인트를 남기고, 그것을 앞 체크포인트로 가리킵니다. 백업 뒤에 남은 체크포인트는 그 기간의 기록으로 그대로 남고, DB는 거기서부터 이어 갑니다(payday#70). 그 체크포인트에 복원한 번호가 함께 남고, `verify`가 `restoring checkpoint N`으로 보여 줍니다.
- 체크포인트 저장소에서 체크포인트를 지우거나 DB의 체크포인트 번호를 손으로 고치지 않습니다. 증거를 지우는 일이고, 삭제를 거부하는 저장소에서는 되지도 않습니다.
- 최신 체크포인트 이후 시점으로 복원할 수 있으면(PostgreSQL WAL 아카이브의 시점 복원) `behind`가 생기지 않아 이 단계도 필요 없습니다.
- 멈춘 동안 실패한 개인정보 삭제는 `accept` 뒤에 다시 실행합니다([5](#5-다시-돌아간-뒤)).

## 행의 봉인과, 올린 뒤 한 번의 받아들임

`audit.digest.key`를 둔 배포에서 `loft trail rows`는 지금 DB의 행을 감사 기록의 지문과 비교합니다. 지문은 개인정보 필드를 뺀 모든 필드를 덮습니다. 비밀(`secret`) 필드도 덮습니다. 개인정보 필드는 **행의 봉인**이 덮습니다(payday#115). 봉인은 행 전체의 MAC이고, 그 행 옆의 DB에만(`rowseal`) 행이 있는 동안 둡니다.

- 감사 기록의 줄은 보관소로 옮겨져, 행이 없어지고 그 사람을 잊은 뒤에도 몇 년씩 남습니다. 그래서 줄에는 개인정보의 MAC을 남기지 않습니다. 키를 가진 사람이 무엇이었는지 맞춰 볼 수 있기 때문입니다.
- 봉인은 행을 쓰는 트랜잭션 안에서 쓰고, 행과 함께 지웁니다. 내보내기에 담지 않고, 복구가 되살린 행을 다시 봉인합니다. 개인정보 삭제는 봉인을 "잊었음"이라는 봉인으로 바꿉니다. 그것은 그 사람의 아무것도 담지 않습니다.
- 서버를 거치지 않고 개인정보 필드를 바꾸면 `differs`, 봉인을 떼어 내도 `differs`, 다른 쓰기의 봉인을 붙이면 `forged`입니다.
- 잊은 사람의 행은 요약 줄에 `N forgotten`으로 셉니다. 지문이 덮는 것만 보증하고, 다음에 서버를 거쳐 쓰면 다시 봉인됩니다.

**이 버전으로 올린 뒤 한 번 받아들입니다.** 올리기 전에 쓴 사람·구성원·초대·알림의 행은 마지막 쓰기가 봉인하지 않았으므로 **봉인 이전**으로 셉니다. 찾을 것이 아니라서 검사는 통과합니다. 대신 그 행의 개인정보 필드는 아무것도 보증하지 않습니다. 개수는 매번 나옵니다. 살펴본 뒤 한 번 받아들이면 봉인됩니다.

```sh
loft trail rows                                                              # `N rows from before seals: …`, 그리고 다이제스트
loft trail rows --accept --of sha256:… --why "이 버전으로 올리기 전에 쓴 행을 봉인함"
loft trail rows                                                              # 봉인 이전의 행 없음
```

- 다른 찾은 것이 없어도 받아들입니다. 받아들임은 그 다이제스트에 대한 것이라, 살펴본 뒤 바뀐 행은 함께 받아들이지 않습니다. 행마다 받아들였다는 기록(`loft.trail.rows.accept`)이 감사 기록에 남고, 이유는 로그에 남습니다.
- 받아들이기 전에는 봉인 이전의 행의 개인정보 필드를 서버를 거치지 않고 바꿔도 찾지 못합니다. 미루지 않습니다.
- 지문이 비밀 필드까지 덮게 되었다고 새로 찾는 것은 없습니다. 이전의 지문은 자기가 덮은 필드를 적어 두었고, 그 필드로만 검사합니다.

**보관 기간이 워크스페이스로 옮긴 버전으로 올린 뒤에도 한 번 받아들입니다**(D36). 마이그레이션이 계약(`tenantcontract`)의 보기·보관·유예·접속기록·복구 기간을 워크스페이스로 옮기고 그 열을 지웁니다. 그 계약 행의 지문은 지운 열까지 덮었으므로, 그 값이 0이 아니던 계약은 `loft trail rows`에서 `differs`로 나옵니다. 마이그레이션이 다시 쓴 행이니 살펴본 뒤 한 번 받아들입니다. 이 마이그레이션은 다시 쓴 행을 감사 기록에 남기지 않습니다. 그때의 `loft migrate`에는 지문의 키가 없었습니다. 워크스페이스 행에 새로 생긴 필드는 이전 지문이 덮지 않으므로 찾는 것이 없습니다.

```sh
loft trail rows                                                              # `differs tenant-contract …`, 그리고 다이제스트
loft trail rows --accept --of sha256:… --why "보관 기간을 워크스페이스로 옮긴 마이그레이션이 계약의 열을 지움"
loft trail rows                                                              # 찾은 것 없음
```

- `differs`가 계약 말고 다른 종류에도 있으면 받아들이지 않고 [4](#4-침해가-의심되거나-원인을-모를-때)로 갑니다.

## 체크포인트의 증인

체크포인트는 바로 앞 체크포인트를 가리키므로, 최신 체크포인트 아래의 사슬은 검사됩니다. 그런데 최신 체크포인트 자체는 DB가 매긴 번호와 체크포인트 저장소만 압니다. DB와 저장소를 모두 쓸 수 있는 사람은 최신 체크포인트 몇 개를 지우고 번호를 되감을 수 있습니다. 그러면 다음 작업은 남은 것 뒤로 번호를 이어 가고, 둘 어디에도 흔적이 남지 않습니다. **증인**은 둘 다 닿지 않는 곳에서 체크포인트를 남길 때마다 들어 두는 것입니다(payday#115). `audit.checkpoints.witnesses`에 적습니다.

| 증인 | 하는 일 | 둘 곳 |
| --- | --- | --- |
| `log:` | 체크포인트마다 로그 한 줄(`trail: a checkpoint, heard`, `k`·`digest`·`prev`)과 게이지 `payday.trail.checkpoint`를 남깁니다. 답은 하지 않습니다. 바깥의 모니터링이 증인이고, [아래의 경보](#증인의-경보)를 걸어야 증인 노릇을 합니다 | 볼륨이 필요 없습니다 |
| `store:<디렉터리>` | 들은 체크포인트를 서명된 그대로 자기 디렉터리에 둡니다. `verify`가 물으면 답합니다 | 보관소와 다른 디스크에, DB·보관소와 다른 자격 증명으로, 되도록 삭제를 거부하는 저장소에. 보관소와 같은 디스크의 증인은 증인이 아닙니다 |

- `deploy/compose`는 둘 다 적습니다. `deploy/k8s`의 base는 `log:`만 적고, `store:`의 볼륨은 컴포넌트 `witness/`가 가져옵니다(`deploy/k8s/README.md`). 개발용 `loft.yaml`은 보관소가 없어 적지 않습니다. 보관소 없이 적은 증인은 시작할 때 거부됩니다.
- 증인이 듣지 못해도 작업은 멈추지 않습니다. 로그에 `trail: a witness did not hear a checkpoint, and the next pass tells it again`을 남기고, 다음 패스가 놓친 것을 오래된 것부터(패스마다 100개까지) 다시 알려 줍니다.
- `loft trail verify`는 답하는 증인마다 마지막으로 들은 것을 보여 줍니다. 첫 체크포인트 전에는 `nothing yet`입니다.

  ```
  heard by store:/var/lib/loft/witness: checkpoint 41, sha256:…, at 2026-10-22T03:12:09Z
  ```
- 증인이 들었는데 DB가 번호를 매기지 않은 체크포인트가 있으면 어떤 작업도 그 번호로 체크포인트를 남기지 않습니다. 번호를 되감았다는 뜻이기 때문입니다. 받아들임은 증인이 들은 모든 번호 다음으로 번호를 매기고, 증인보다 뒤처진 DB는 복원으로만(`--restored`) 받아들입니다.

### `unkept` — "the chain was cut short there"

```
unkept sha256:… checkpoint 43: witness store:… heard it, and the store does not keep it: the newest the store keeps is 41, and the chain was cut short there
```

**뜻:** 증인이 들은 체크포인트가 저장소의 최신보다 뒤인데, 저장소에 없습니다. 누군가 최신 체크포인트를 지웠거나, 저장소나 DB를 오래된 사본에서 되살렸습니다.

1. [1](#1-확인하고-남기기)처럼 증거부터 남깁니다. 증인의 저장소도 그대로 복사해 둡니다. 증인이 들은 것이 그때 사슬이 말한 것입니다.
2. 체크포인트 저장소가 버전을 남기는 곳(S3 Object Lock, WORM)이면 지운 체크포인트가 삭제 표시 뒤에 그대로 있습니다. 되살리고 다시 `verify`합니다.
3. DB나 저장소를 백업에서 되살린 것이 작업 기록으로 확인되면, `lost`와 `missing`을 하나씩 확인한 뒤 복원으로 받아들입니다. `verify`가 DB가 뒤처졌다고 말하면 `--restored`를 붙입니다([DB를 백업에서 복원했을 때](#db를-백업에서-복원했을-때)).
4. 그렇지 않으면 [4](#4-침해가-의심되거나-원인을-모를-때)입니다. DB·보관소·체크포인트 저장소의 자격 증명을 바꾸고, 원인을 안 뒤에 무엇이 있었는지 `--why`에 적어 받아들입니다.

최신보다 아래의 `unkept`, 곧 증인이 들었는데 저장소에 없는 중간의 체크포인트도 같습니다.

### `rewritten` — 증인이 같은 번호를 두 번 들음

```
rewritten sha256:A checkpoint 40: witness store:… heard it as sha256:A, and again as sha256:B: the count was wound back and the number taken again
```

**뜻:** 증인이 같은 번호를 서로 다른 두 문장으로 들었습니다. 모든 증인이 듣지 못하는 동안(꺼졌거나 막혔거나) 누군가 최신 체크포인트를 지우고 번호를 되감아 다시 매겼습니다. 증인은 돌아오면 놓친 것을 모두 들으므로 증인의 최신은 배포의 최신과 같아지고, 맨 위에서는 드러나지 않습니다. 그래서 아래쪽의 번호마다 두 문장의 쌍으로 드러납니다. 쌍마다 하나의 발견입니다.

1. 증거를 남깁니다. 증인의 저장소까지 복사합니다.
2. 증인이 언제 듣지 못했는지 로그에서 찾고(`trail: a witness did not hear a checkpoint`), 그 사이에 무엇이 번호를 되감았는지 봅니다. 작업 기록으로 확인되는 복원이면 사고가 아닙니다.
3. 원인을 알면 받아들입니다. 받아들임은 보여 준 쌍만 받아들입니다. 받아들인 뒤에 되감은 것과 보여 주지 않은 쌍은 그다음 `verify`가 다시 찾고, 같은 번호의 세 번째 문장도 새 쌍입니다. `verify`의 받아들임 줄에 `heard twice N`으로 남습니다.
4. 원인을 모르면 [4](#4-침해가-의심되거나-원인을-모를-때)입니다.

`heard it as …, and the store keeps it as something else`이면 저장소의 체크포인트를 다른 것으로 덮어쓴 것입니다. 사고로 다룹니다.

### `unheard`

```
unheard sha256:… checkpoint 41: taken 49h0m0s ago, and no witness that answers heard it
```

**뜻:** 저장소의 최신 체크포인트가 `audit.checkpoints.hear_within`(비우면 `audit.every`의 두 배)보다 오래되었는데, 답하는 증인 누구도 듣지 못했습니다. 증인이 들을 수 없거나(볼륨이 빠짐, 디스크가 참, 권한이 없음), 누군가 자른 것이 드러나지 않게 증인을 막고 있습니다.

- 로그의 `trail: a witness did not hear a checkpoint`가 어느 증인이 왜 못 들었는지 말합니다. 증인을 고치면 다음 패스가 놓친 것을 모두 알려 주고, 최신을 들으면 이 발견은 사라집니다. 받아들일 것이 없습니다.
- 증인을 고쳤는데도 남거나, 막힌 이유를 모르면 [4](#4-침해가-의심되거나-원인을-모를-때)입니다.

### `forged` — 증인의 답의 서명이 틀림

```
forged sha256:… checkpoint 41: witness store:… answers that it heard it, and its signature is not good
```

**뜻:** 증인이 들었다고 답한 문장이 배포가 서명한 것이 아닙니다. 누군가 증인의 저장소에 썼습니다.

- 증인의 저장소는 Loft만 씁니다. 누가 또 쓸 수 있는지 찾아 그 권한을 없애고, 저장소의 버전이나 스냅숏에서 되돌립니다.
- 그때까지 사슬은 그 증인에게는 대어 보지 못하고, 다른 증인에게는 그대로 대어 봅니다.
- [4](#4-침해가-의심되거나-원인을-모를-때)로 다룹니다.

### 증인의 경보

`log:`는 이 경보가 있어야 증인입니다. 무엇으로 거는지는 [관측](observe.md#경보)에 있습니다.

1. **게이지 `payday.trail.checkpoint`가 내려감:** 번호를 되감았습니다. Prometheus라면 `payday_trail_checkpoint < max_over_time(payday_trail_checkpoint[30d])`입니다.
2. **로그 `trail: a checkpoint, heard`에 같은 `k`가 서로 다른 `digest`로 두 줄:** 같은 번호를 다시 썼습니다.
3. **게이지가 패스 두 번보다 오래 움직이지 않음:** 패스마다 체크포인트를 남기는 배포라면 겁니다. 증인이 듣지 못하게 막혔습니다.

`store:`는 `verify`가 물으므로 경보가 필요 없습니다.

## 막기

- **일정**: `loft trail verify`를 매일, `--full`을 주 1회 이상 돌리고, 0이 아닌 종료를 경보로 받습니다. 접속기록의 정기 점검 근거로도 남습니다.
- **경보**: 로그의 `` `trail verify` ``, 그리고 [증인의 경보](#증인의-경보) 셋.
- **증인을 둡니다**: `log:`와, 보관소와 다른 디스크의 `store:`([체크포인트의 증인](#체크포인트의-증인)).
- **체크포인트는 보관소와 다른 곳에**, 삭제를 거부하는 저장소에 둡니다(`audit.checkpoints.dir`과 `audit.checkpoints.write_once`, 또는 S3 Object Lock 규정 준수(compliance) 모드). 보관소와 다른 자격 증명으로 씁니다.
- **서명 키는 장치에 두는 편이 안전합니다.** 파일 키는 프로세스를 가진 사람이 읽어 가져갈 수 있고, 장치(HSM·TPM·KMS)의 키는 가져갈 수 없습니다. payday는 `pkcs11:`, `tpm:`, `hashivault:`, `awskms:`를 받지만 지금의 loft는 그중 아무것도 링크하지 않아 파일이나 PEM만 받습니다. 어디에 둘지는 loft#35에서 정합니다.
- **키를 바꿀 때**는 새 키를 `audit.checkpoints.key`에, 이전 공개 키를 `audit.checkpoints.trust`에 넣고 `verify`합니다.
- **DB를 복원하면** 위의 절차대로 `verify`와 `accept`를 한 번 합니다. 최신 체크포인트 이후 시점으로 복원하면 그것도 필요 없습니다.
- **DB와 보관소를 모두 쓸 수 있는 사람과 자격 증명을 줄입니다.** 체크포인트와 서명이 막는 것은 바로 그 사람입니다.
